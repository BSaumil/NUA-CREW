## Architecture
```
Internet ──443──> ALB (public subnets) ──8000──> API tasks (private subnets)
                                                   │            │
                                         PostgreSQL 16 (RDS)   Redis (TLS + auth token)
Worker task (no inbound) ───────────────────────────┘
One-off migration task (migrator credential only)
S3 documents bucket (private, KMS) and access-log bucket
Vercel: marketing site (live), candidate web, employer web (separate projects, not connected)
```
API, worker and the one-off migration task run from one immutable image digest on Fargate. The database, Redis and tasks sit in private subnets; only the load balancer accepts internet traffic, and only from `alb_ingress_cidrs` (empty means closed).

## Security properties, as written in the code
- **Credentials are split.** The runtime role cannot read the migration DSN; only the migration task's execution role can. The RDS master credential is managed by RDS and used only for the one-off role bootstrap. The migration task also receives the JWT secret because the application refuses to load settings outside development without one.
- **Secrets fail closed.** The owner-supplied secrets (`jwt-secret`, `database-url`, `migration-database-url`) are created empty. A task referencing a secret with no value does not start.
- **Everything risky is OFF, explicitly:** `NUA_DOCUMENT_STORAGE=disabled`, `NUA_PUSH_PROVIDER=none`, `NUA_STRIPE_MODE=disabled`, `NUA_PAID_ADVERTISING_ENABLED=false`, `NUA_BILLING_TERMS_APPROVED=false`, `NUA_ENV=staging`. Task roles get no S3 access unless `enable_document_access` is set.
- **CORS is exact.** `cors_origins` rejects wildcards, non-HTTPS values and paths at plan time.
- **Real client addresses.** The auth rate limiter keys on the client address, and behind a load balancer that is only correct if uvicorn trusts the forwarded header. The tasks set `FORWARDED_ALLOW_IPS` to the VPC range (uvicorn supports CIDR; verified in the installed version).
- **Encryption and logs.** One customer-managed key (rotation on) covers RDS, Redis, the documents bucket, secrets, ECR, and log groups. TLS is required for the database (`rds.force_ssl`), Redis, S3 and the load balancer (TLS 1.2+ policy, HTTP redirects to HTTPS). VPC flow logs, load balancer and S3 access logs, RDS Performance Insights and enhanced monitoring are on.
- **Rollback.** Services use a deployment circuit breaker with rollback; images are immutable and pinned by digest, and the last 30 are kept for rollback.

## Health checks
The container and the load balancer check `/healthz` (liveness). `/readyz` also checks the database, so using it for the load balancer would make a database outage replace healthy tasks and worsen it; it is covered by the smoke test instead. The worker has no HTTP port; a log metric on the `pass complete` line drives a "worker stalled" alarm (no pass in 15 minutes, or not running).

## Cost drivers and budget
No dollar estimate is made here: prices were not verified and would be invented. The drivers, and the variable that controls each, are: NAT gateway (`nat_gateway_count`), RDS instance and storage (`db_instance_class`, `db_allocated_storage_gb`, `db_multi_az`), Fargate CPU and memory (`api_cpu`, `api_memory`, `worker_cpu`, `worker_memory`, desired counts), ElastiCache node (`redis_node_type`), the load balancer, VPC flow logs and log retention (`log_retention_days`). Produce the number with `terraform plan` plus the AWS Pricing Calculator before any apply. A monthly budget (set by the owner, no default) alerts at 80% actual and 100% forecast.

## What is NOT done
- **ClamAV / malware scanning** is not in this module. Uploads stay disabled until a separate, isolated scanner exists and is accepted.
- **Database role bootstrap.** `db/roles/bootstrap.sql` must run once against the private database using the RDS master secret; the mechanism (a one-off task with a `psql` image) is not written.
- **Image push and the chicken-and-egg.** The task definitions need an image digest at plan time, but the registry is created by this module. Plan: create the registry first (`terraform apply -target=aws_ecr_repository.api`, which includes the key), push the image, then apply the rest. Not exercised.
- **CI deployment role** (GitHub OIDC), the remote state backend, DNS, the two Vercel projects, and the Terraform `plan` itself.
- **API reference exposure:** `/docs` and `/openapi.json` return 200 on the local API. Decide whether they should be public in staging.
- **The Docker image was not built here** (no Docker daemon). The existing `staging-container` workflow builds it in CI.

## Order of operations (each step needs its own approval)
1. Owner: AWS account, state backend, budget, ACM certificate, hostnames.
2. `terraform plan -out`, reviewed by the owner and ChatGPT. **No apply without sign-off.**
3. Registry first, then push the image by digest.
4. Apply the rest; owner fills the three secrets directly in Secrets Manager.
5. Bootstrap database roles once; run the migration task (`outputs.tf` gives the `run-task` inputs) after the reviewed preflight and backup.
6. Start services; run `scripts/staging-smoke.sh`, then the browser journey and the isolation tests against staging.
